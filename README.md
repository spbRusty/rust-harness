# rust-harness

Небольшая локальная обвязка на Rust вокруг локальных языковых моделей. Сейчас основной backend — Ollama.

Цель проекта — не сделать очередной универсальный AI-фреймворк, а собрать контролируемое ядро, поверх которого можно строить оркестраторы для разных задач: разработка игр, программирование, работа с 1С и другие среды.

## Что сейчас умеет harness

- подключаться к локальной модели через Ollama;
- выполнять агентский цикл `задача → модель → инструмент → результат → модель`;
- читать, искать и записывать файлы в пределах workspace;
- запускать программы без shell-строки и с ограничением времени;
- подключать MCP-серверы через stdio;
- передавать модели MCP-инструменты;
- автоматически проверять изменённый проект после изменений;
- вести состояние запуска и явно завершать его как `done`, `failed`, `blocked` или `max_iterations`;
- ограничивать число verification cycles и итераций;
- сокращать старые результаты инструментов в контексте;
- делегировать отдельные задачи специализированным подагентам.

## Агентский цикл

Главный принцип проекта — модель не является единственным источником истины о результате.

```text
                 задача
                   │
                   ▼
             ┌───────────┐
             │   Agent   │
             └─────┬─────┘
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       tools      task      MCP
          │        │        │
          └────────┼────────┘
                   ▼
                результат
                   │
                   ▼
              verification
                   │
             ┌─────┴─────┐
             │           │
           failed      passed
             │           │
             ▼           ▼
          исправить     done
             │
             └────→ verification
```

После изменения файлов harness запускает доступную проверку проекта. Ошибка возвращается модели как часть следующего шага. Успешный текстовый ответ модели сам по себе не считается доказательством того, что изменение работает.

## Explorer / Executor / Reviewer

Главный агент может делегировать изолированные подзадачи через инструмент `task`.

### Explorer

Только исследует проект:

- `list_dir`;
- `project_search`;
- `read_file`.

Не может менять файлы и запускать команды.

### Executor

Выполняет изменения:

- исследует проект;
- пишет файлы;
- запускает команды;
- возвращает результат родительскому агенту.

### Reviewer

Проверяет результат:

- читает изменённые и связанные файлы;
- ищет дефекты;
- может запускать проверки;
- не может изменять файлы.

Это намеренно сделано через один `task` router. Добавление новой роли не требует переделки основного агентского цикла.

## Verification

Verification — отдельный слой, а не обещание модели.

Сейчас поддерживаются:

- Rust: `cargo test`;
- Node-проекты: `npm test`, если есть соответствующий script;
- Node-проекты: `npm run build`, если test отсутствует, но есть build;
- проекты без известного gate получают статус `skipped`.

Каждая проверка возвращает структурированный результат с `status`, командой и выводом.

Harness не должен утверждать «всё работает», если проверка не выполнялась.

## MCP

MCP — внешний слой инструментов. Сервер запускается отдельным процессом через stdio, после чего harness получает его инструменты и добавляет их в общий registry.

```text
Rust Harness
    │
    ├── native tools
    │     ├── files
    │     ├── search
    │     └── commands
    │
    └── MCP
          ├── Playwright
          ├── браузерные инструменты
          ├── GitHub
          └── другие MCP-серверы
```

MCP не привязан к конкретной среде. Поэтому тот же механизм может использоваться и для разработки Roblox, и для работы с 1С.

## CLI

Проверить модели:

```bash
cargo run -- models
```

Показать инструменты:

```bash
cargo run -- tools
```

Запустить основного агента:

```bash
cargo run -- run "посмотри проект и объясни его структуру"
```

Запустить конкретную роль отдельно:

```bash
cargo run -- delegate explorer "изучи проект и найди файлы, связанные с загрузкой уровней"
cargo run -- delegate executor "исправь найденную проблему и проверь результат"
cargo run -- delegate reviewer "проверь результат и найди оставшиеся проблемы"
```

## Конфигурация

```toml
[model]
endpoint = "http://127.0.0.1:11434"
name = "qwen2.5:7b"

[workspace]
path = "."

[[mcp]]
name = "example"
command = "npx"
args = ["some-mcp-server"]
```

Модель можно заменить на любую модель, доступную через Ollama.

## Принципы

1. **Loop важнее prompt.** Главный результат даёт связка действия, наблюдения и проверки.
2. **Verification внешняя.** Модель не может сама подтвердить собственную работу.
3. **Роли ограничены инструментами.** Explorer не пишет, Reviewer не редактирует.
4. **Контекст ограничен.** Старые результаты инструментов не должны бесконечно расти.
5. **Остановка явная.** У каждого запуска есть статус и причина остановки.
6. **MCP остаётся внешним интерфейсом.** Он не должен зашиваться в конкретный тип проекта.

## Основа архитектуры

Архитектура опирается на несколько практических идей из современных coding-agent harnesses: bounded tool loop, ограниченный контекст, делегирование подагентам, проектный verification contract и разделение ролей. Vercel отдельно подчёркивает необходимость реальных verification gates и scoped claims, а oh-my-openagent использует разделение ролей, MCP и skills как независимые расширения.

## Статус

Проект находится в активной разработке. Сейчас сформировано ядро: модель, tools, MCP, state, verification и базовая оркестрация Explorer / Executor / Reviewer.

Следующий слой — не новые «умные» агенты, а усиление маршрутизации, разрешений, project context (`AGENTS.md`), более точного verification и подключения MCP/skills без изменения ядра.
